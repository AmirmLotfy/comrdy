# COMRDY custom domain cutover

Status, November 1, 2026: `comrdy.com` is planned but is not purchased, connected, or verified for this project. The submitted working demo remains https://comrdy.vercel.app. Devpost's public story and private judge instructions identify the planned domain as inactive; the required hosted-demo field still uses the working Vercel URL.

## After the owner buys the domain

1. In Vercel, add `comrdy.com` to `mellardoos-projects/comrdy`. With the currently installed CLI, `vercel domains add comrdy.com comrdy --scope mellardoos-projects` is the available add operation. Do not use `--force` or remove an existing assignment. Configure the exact ownership and DNS records Vercel reports at the authoritative DNS provider; preserve unrelated records. Verify ownership, DNS, and the HTTPS certificate before presenting the domain as active. If the command or Vercel dashboard reports a conflict, resolve it without detaching another project.
2. The safest initial connection is a Vercel redirect from `comrdy.com` to `https://comrdy.vercel.app`, retaining all current paths and query strings. Check that the project dashboard supports and applies the desired redirect, then verify the root, `/judges`, `/readiness`, and `/demo` in a fresh browser session. This keeps the already-qualified application origin and PayPal callbacks on the existing hostname. Do not point judges to the new domain until redirect and TLS checks pass.
3. Once verified, update the existing Devpost project story and private testing instructions to remove the inactive-domain note. Add the new URL to the public “Try it out” links and, if desired, replace the required hosted-demo URL only after end-to-end checks. Keep a working Vercel fallback, and verify that finalization still shows **SUBMITTED** and that the submitted video, screenshots, links, and private judge instructions remain intact. Update the YouTube description only if appropriate; the video itself contains the existing working URL.

## If serving the application directly on the custom domain

This requires a separately tested coordinated cutover, not just DNS. The API's POST origin check compares against `APP_URL`, and the worker's shopper allowlist also uses that origin. A direct custom-domain visit with the current `APP_URL` can therefore load pages but reject interactions with HTTP 403. PayPal return URLs, merchant browser execution, metadata, the Vercel deployment, the Render worker, and the configured Sandbox webhook must remain coherent. Plan and stage both environment changes, callback and webhook changes, rollback, and a fresh Sandbox buyer-approved end-to-end check before advertising this mode. Preserve the qualified historical evidence and its original URLs and revision; do not relabel it as requalified on the new origin.
