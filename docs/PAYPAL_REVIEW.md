# PayPal documentation review — 2026-11-01

Reviewed the current official PayPal references against `src/providers/paypal.ts`, the Sandbox worker, return handling and setup instructions. This was a read-only source/documentation review: no credentials, dashboard changes, payment requests or tests were used. It does not qualify the integration against PayPal.

## Assessment

No confirmed blocking API-contract mismatch was found in the current single-merchant Sandbox flow. Preserve the separate create/approve/authorize/capture steps, deterministic gate, exact USD amount, final capture, and independent void readback. Do not replace this flow with immediate order capture or introduce vaulting, refunds, partner onboarding or live payments for this milestone.

## Required for this project's provider qualification

1. **Use actual Sandbox app events for postback signature verification.** `PayPalSandboxAdapter.verifyWebhook()` preserves the original event JSON while sending the transmission headers and configured webhook ID to PayPal. That matches the documented postback method. PayPal's simulator events cannot be verified using that method; a simulator delivery is therefore not a positive acceptance test for this adapter. Generate an actual Sandbox-app payment event, verify acceptance and durable deduplication, then verify rejection when its signature/body is altered. Keep public HTTPS port 443 reachable. PayPal retries unsuccessful deliveries up to 25 times over three days. [Webhook integration guide](https://developer.paypal.com/api/rest/webhooks/rest/)

2. **Configure the correct v2 lifecycle events.** Register `PAYMENT.AUTHORIZATION.CREATED`, `PAYMENT.AUTHORIZATION.VOIDED`, `PAYMENT.CAPTURE.PENDING`, `PAYMENT.CAPTURE.COMPLETED`, and `PAYMENT.CAPTURE.DECLINED`. The v2 event is **DECLINED**; **DENIED** appears in the v1 list. `CHECKOUT.ORDER.APPROVED` is optional observation: the current app deliberately waits for the buyer return/owner action and retrieves PayPal state before authorization. Reversal/refund notifications can be observed if desired, but enabling them does not authorize refund functionality or related product claims. [Official event names](https://developer.paypal.com/api/rest/webhooks/event-names/)

3. **Verify request identity and actual provider outcomes.** The implementation persists a distinct UUID-shaped request ID per operation and reuses its original payload on the single permitted retry. Preserve that behavior. PayPal permits retry of uncertain requests only while it retains the key; concurrent requests with one key can produce an error for the second request. A key is not a substitute for resource retrieval. The app's one-hour/two-dispatch ceiling is an application policy, not a promise of a universal PayPal retention period. [Idempotency guidance](https://developer.paypal.com/api/rest/reference/idempotency/)

4. **Check the current endpoint-specific retention instead of assuming one global TTL.** The Orders SDK create reference explicitly documents six-hour key storage, with an account-arranged extension. The app's one-hour create replay bound is shorter. The current capture/void endpoint pages document request-ID support but do not state a corresponding TTL; retain the short bound and provider-readback requirement. Do not extrapolate a generic 45-day example to every operation. [Create-order SDK reference](https://developer.paypal.com/sdk/orders/v2/orders-create/)

5. **Keep capture and void assertions precise.** The capture adapter uses the authorization endpoint, explicit amount and `final_capture: true`; qualification must confirm the retrieved COMPLETED capture, exact amount and final flag. No order-status-only paid claim is acceptable. The void endpoint currently documents `PayPal-Request-Id` support and both 200/204 success responses; keep the header and retrieve the authorization separately to confirm VOIDED. [Capture authorization](https://developer.paypal.com/api/payments/v2/authorizations-capture), [Void authorization](https://developer.paypal.com/api/payments/v2/authorizations-void)

## Actionable source findings and optional hardening

**P2 diagnostic gap — preserve safe error details.** `src/providers/paypal.ts:277–293` reads only top-level `name` and `debug_id`; `src/server/sandbox.ts` persists only the resulting generic error code. Different 422 issues therefore become indistinguishable during manual reconciliation. Recommended correction: normalize `details[].issue` and optional `details[].field`, preserve the provider debug ID in private operator evidence, and expose only a sanitized issue code to the UI. Never persist raw provider bodies or buyer values. This is operational hardening, not evidence of an invalid payment request. PayPal endpoint references link their specific errors; retain fail-closed settlement behavior while improving diagnosis. [Capture endpoint reference](https://developer.paypal.com/api/payments/v2/authorizations-capture)

**P2 delivery gap — unmatched verified events are marked consumed.** `src/server/sandbox.ts:1247–1280` acknowledges and deduplicates an event even when its resource has not yet been associated with a run. An event arriving before a provider response is durably installed cannot be attached by a later identical delivery. Current command reconciliation often recovers independently, so this is not a demonstrated payment-loss defect. Recommended correction: retain a minimal redacted unmatched receipt and attempt association after the order/authorization ID is installed; preserve idempotent processing. This recommendation follows from the local race, not a new PayPal requirement. PayPal delivery retries alone cannot repair an event already acknowledged with 2xx. [Webhook delivery behavior](https://developer.paypal.com/api/rest/webhooks/rest/)

**Scope limitation — physical item, suppressed address.** `createOrder()` declares `PHYSICAL_GOODS` but uses `NO_SHIPPING`, and the app does not implement real fulfillment. For this controlled Sandbox lab, state that shipping and tax are merchant test amounts and no delivery is promised. If actual physical checkout becomes authorized scope later, select the appropriate shipping preference and bind address/merchant evidence privately; never silently treat `NO_SHIPPING` as delivery qualification. The documented field supports suppressing the shipping address; it is not an API rejection by itself. [Create-order reference](https://developer.paypal.com/sdk/orders/v2/orders-create/)

**Optional — local cryptographic webhook verification.** PayPal prefers self-verification to avoid the extra postback request and dependency. The implemented postback method remains supported and is adequate for this bounded lab. Do not expand scope to certificate caching/cryptographic verification merely to replace a working supported path. [Verification methods](https://developer.paypal.com/api/rest/webhooks/rest/)

## Buyer-return acceptance

Source inspection confirms that the adapter uses `payment_source.paypal.experience_context`, accepts the provider's Sandbox approval/payer-action link, and never trusts the return query as payment proof. The case view passes the returned `token` as the order ID; the service matches it to the owned run, then the worker retrieves the order and requires APPROVED before authorization. Verify this full round trip with the same application origin/session, plus cancel, duplicate return, wrong token and refresh. This is a remaining live check, not a reason to put buyer credentials in the app or browser agent.

The six linked official sources support this bounded review. Endpoint documentation and account behavior may evolve; retain the exact successful Sandbox release receipts alongside this review rather than treating documentation as observed provider proof.
